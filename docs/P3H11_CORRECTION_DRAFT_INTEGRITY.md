# P3H.11: Correction Drafting Integrity, Confirmed-Facts Invariant & Attestation Audit

## Executive Overview

This report documents the verification of the Administrative Correction Drafting Engine (`backend/app/services/correction_draft_service.py` and `backend/app/services/document_generator.py`) under milestone P3H.11.

The primary safety invariant of the drafting engine is: **Only Confirmed Facts May Enter Official Drafts.** Automated drafting of formal representations to government authorities (e.g. UIDAI Regional Office, Income Tax Assessing Officer, EPFO Regional Commissioner, or Regional Passport Office) must never rely on unverified OCR text or outdated demographic facts.

---

## 1. Confirmed-Facts Invariant Architecture

### 1.1 Invariant Rules
1. **Human Confirmation Barrier**: A citizen document cannot be used as the evidentiary foundation for a correction draft unless `is_user_confirmed == True`.
2. **Dynamic Invalidation**: If any demographic field is modified via `PATCH /api/v1/documents/{id}/fields`, `is_user_confirmed` is immediately set to `False`. Any active draft linked to that document must be invalidated or re-generated.
3. **Advisory Watermarking**: Every generated PDF and UI draft preview contains an indelible diagonal watermark:
   `AI-GENERATED SUPPORTING DRAFT • NOT AN OFFICIAL FORM`
4. **Non-Delegated Submission Boundary**: The draft must explicitly inform the citizen that:
   - CONVELINA cannot submit petitions on behalf of citizens.
   - The citizen must print the draft on physical paper, review every statement personally, affix their physical signature, attach attested supporting photocopies, and submit it directly to the designated authority.

## 2. Invariant Enforcement & Automated Verification

### 2.1 Confirmation Security Verification (`test_p3h11_confirmation_security.py`)
- **Unconfirmed Document Rejection**: `test_modification_invalidates_confirmation` verified that updating extracted fields resets confirmation:
  ```python
  # Initial confirmation
  res = client.post(f"/api/v1/documents/{doc_id}/confirm", headers=headers)
  assert res.json()["is_user_confirmed"] is True

  # Modifying fields
  res = client.patch(
      f"/api/v1/documents/{doc_id}/fields",
      json={"extracted_fields": {"name": "AARAV VIKRAM SHARMA"}},
      headers=headers,
  )
  assert res.json()["is_user_confirmed"] is False  # Invariant strictly preserved
  ```

## 3. Cryptographic Platform Attestation (Ed25519)

### 3.1 Attestation Protocol
Upon final citizen review, the citizen clicks "Confirm Draft" to apply the platform's cryptographic seal:
1. **Canonical JSON Serialization**: The draft payload (citizen ID, conflict ID, source document hashes, generated text, and timestamp) is normalized using RFC 8785 canonical JSON formatting.
2. **SHA-256 Integrity Hash**: A cryptographic hash is calculated over the canonical payload.
3. **Ed25519 Signing**: The platform's active private key signs the canonical payload using Ed25519 (RFC 8032).
4. **Public Verification**: The resulting base64 signature and key fingerprint are stored in `correction_drafts.ed25519_signature` and `correction_drafts.key_fingerprint`.
5. **Keystore Integrity**: Public keys are cataloged in `pki_keys` and visible to administrators on `/admin` and `/dev/explorer`.

### 3.2 Distinction from Statutory eSign
- The platform UI explicitly labels this seal as an **"Ed25519 Platform Attestation"**.
- It provides mathematical proof that the draft was generated by CONVELINA at a specific timestamp and has not been altered since generation.
- It is clearly disclaimed as distinct from an Aadhaar eSign or IT Act Class 3 digital signature.

## 4. Verification Sign-Off

The correction drafting engine strictly adheres to the confirmed-facts invariant, applies indelible advisory watermarks, and seals drafts with tamper-evident Ed25519 attestations.
